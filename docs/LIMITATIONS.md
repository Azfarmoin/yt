# Known limitations (read before relying on this)

1. **Recitation audio was not obtained in the build environment** (all recitation hosts were blocked by the sandbox network policy).
   The sample video is therefore text-only and labeled so. The download/mix code path is tested only with a synthetic tone.
2. **YouTube publishing is untested against a live account.** The code follows Google's documented OAuth + resumable-upload flow.
   Expect to debug the first real upload with `privacy: private`. New/unverified API projects may be forced to private by Google;
   OAuth apps in "Testing" mode have refresh tokens that expire after 7 days (publish the consent screen to avoid it).
3. **Content volume is bounded by the curated catalog**: 20 Quran references + 1 hadith + any stories you author. When the catalog is
   exhausted the engine skips the day rather than invent content. Extend `ivs/catalog.py` (verified at run time).
4. **No generative script/topic AI.** A free local LLM could draft explainers, but religious claims would then need the same
   human review as stories; it is deliberately left out rather than shipped unreliable.
5. **Recitation ↔ text timing is approximate** for multi-ayah/chunked screens (proportional by text length); each ayah is
   synchronized to its own audio file. Word-level alignment (whisper.cpp) is not included.
6. **Hadith**: the source's Urdu/English translations are third-party and vary in quality; the data source carries no
   per-narration grading, so the grading shown is a collection-level note. Every hadith item requires human review.
7. **Automated checks do not verify religious correctness.** Cross-edition comparison detects corruption/shifted verses, not
   scholarly accuracy. Have a qualified person review the catalog and translations you choose.
8. **Narration (Piper)**: not wired by default; Urdu voice availability must be confirmed before enabling.
9. **Scheduler** runs only while your PC/process is on; there is no 24/7 guarantee. GitHub Actions is not used for rendering.
10. Other platforms (Instagram/Facebook/TikTok) require app review and business accounts; not implemented.
11. Visuals are generated geometric patterns only (zero license exposure). No stock footage module.
12. Urdu lines in Nastaliq can leave a single-word last line on narrow wraps; legible, but not typographically ideal.
13. **Script lines are editorial, not scholarly.** They were written by the tool author, restricted to what each verse literally says, with Urdu wording that a native reader should check. Until a key is listed in `SCRIPT_REVIEWED`, the item is held in `needs_review`.
14. **Scripts are catalog-bound.** There is no run-time text generation, so new videos need new `SCRIPTS` entries (a missing entry just means the video has no context/takeaway scenes).
15. **VFX** are intentionally restrained (no animated figures, no footage). Rendering with effects takes about 80 s per video on a 2-core machine; set `video.vfx.enabled: false` to speed up.
16. Sound effects/music are still not included (nothing is mixed under recitation).
17. **Animated stories show scenery only.** By design (and by test) nothing depicts people, prophets or sacred figures, so scenes are atmosphere, not literal illustrations of the events. The scene tag is chosen by the author.
18. **Story content is author-supplied.** The two included stories use only Quran verses (verified by reference) plus one-line narration/takeaway written by the tool author; they are held in `needs_review` and the Urdu wording should be checked by a native reader. The engine does not write stories itself.
19. In stacked layout (Arabic + Urdu + English on one screen) long ayat are split into several screens to stay above the readability floor, which makes some stories run near the 60 s limit (the Yunus sample is 54 s).
20. **Not a Blender/3D "animated movie".** Blender was not used. Animation is lightweight 2D/2.5D: parallax scenery, one walk cycle per silhouette type (walker, spearman, traveller, elephant, bird), no sitting/running/interacting characters, no trees, rain, fire, rivers or cloth. Everything is procedural so it is free and automatic; it looks like a stylised motion graphic, not a studio film.
21. **Silhouettes are generic.** They are labelled as illustration only and make no claim to depict real people. Scenes about Prophets show scenery only (the engine has no prophet/Companion actor and rejects such actions).
22. **Narration quality.** Kokoro English is natural-sounding but not emotional; there is no pace/emotion control beyond fixed speed and pauses. Urdu (eSpeak NG) is clearly robotic: consider recording your own Urdu narration instead. Neither voice may ever be presented as a scholar or reciter (the outro and description say it is synthetic).
23. **Sound design is basic** (synthesized, sparse): no horses, doors, rain, fire, or scene-transition effects. Effects are muted under verses.
24. **Hook/title/engagement logic is rule-based**, not an LLM or a human editor. The 80-point gate catches missing structure and clickbait wording; it cannot tell whether a hook is genuinely moving.
25. **Authenticity checks are mechanical.** The claims table records provenance and review status; it does not establish scholarly correctness. Stories are author-written and need review by someone qualified; the author-written narration is limited to literal readings of the cited verses.
26. **Recitation is gated by you.** It cannot be verified automatically that a recording may be reused; the engine stays text-only until you confirm. Quran formats B (reflection) and D (learning with word highlighting/tajweed) are not implemented; formats A/C are covered by single-passage videos.

27. **3D (Blender) is real but slow and stylized.** `ivs/bl_scene.py` builds procedural terrain, sky, ocean, clouds, faceless robed figures with walk cycles, an elephant with leg cycles and flapping birds, and moves a real camera (dolly, truck, crane, orbit, low push, follow). Measured on the 2-core CPU-only sandbox: Cycles draft (360x640, 12 samples) ~8-12 s/frame, so a 2.5 s draft shot takes ~5 min; 1080x1920 full tier would be roughly 10x slower per frame. A whole 40 s film in 3D at full quality is hours on a CPU. Hence the **hybrid**: 3D for the hook and the conflict scene, the 2.5D engine for the rest. Use a machine with a GPU for the `hd`/`full` tiers. The look is "low-poly stylized", not photoreal; no cloth simulation, fluid simulation or fire yet.
28. **Not implemented from the 3D spec:** diorama/isometric/map/cutaway techniques, rain/flood fluid simulation, villages/markets/buildings, hands offering food, sitting/carrying/offering animations, historical-accuracy checking of architecture or clothing. The storyboard only offers the two techniques that exist (`blender_3d`, `layered_2_5d`).
29. **Creative direction is rule-based, not an AI director.** It stages the lines a human wrote and verified; it picks cameras, palettes, transitions and sounds that differ from recent videos (`direction_log`), and QC-checks the storyboard (hook first, no consecutive repeated camera, >=3 camera moves, actors whitelist, no forbidden visual terms, durations). It cannot judge historical accuracy; the story reviewer must.
30. **Characters are generic.** They are not depictions of any historical person. No Prophet/Allah/Companion actor exists, and storyboard QC rejects any other actor type or forbidden term in the visual text.
31. **3D shots are not yet wired into the automatic `make`/scheduler render** (they are produced with `python -m ivs shot <story> <scene> --tier draft|hd|full`), because a CPU render would block the daily schedule. The 2.5D path still renders every video automatically.

32. **Long films (60-120 s).** Stories are now authored at ~80-100 s (hook, context, verse text, narration in English + Urdu, SFX, ambience, subtitles, takeaway, outro). Measured: Al-Fil renders at 85 s. The extra narration lines are the author's words and are flagged for human review against tafsir.
33. **3D coverage is a budget, not the whole film.** `three_d.max_seconds` (default 30 s) of each film is Blender; the rest is 2.5D. Draft tier is 360x640 at 8 fps, interpolated to 24 fps and upscaled to 1080x1920, so 3D shots look softer than the 2.5D layers. Render time is ~6-9 s/frame on this 2-core CPU, i.e. ~40-50 minutes of rendering for one film. `python -m ivs film <story> --tier hd|full` on a faster machine gives sharper shots.
34. **3D is overlaid with the same subtitle panel as 2.5D**, which covers the middle of the frame; subjects are framed in the lower third to compensate. Empty night landscapes are kept in 2.5D because they render as near-black.
35. **Model detail is stylized low-poly:** folded robes, turbans, belts, sleeves/hands, sandals, tusked elephants with blankets and canopy, camels, a ship, palms, rocks, tents. No cloth/fluid simulation, no fire, no buildings/villages, camels and the ship are simple.

36. **AI script assistant (`python -m ivs draft-story 105:1-5 --id x --title "..." [--notes notes.yaml]`).** Uses a local free LLM through Ollama if running, otherwise a deterministic fallback. The AI only rephrases the verified translation and YOUR sourced notes: lines are dropped if they contain Arabic/tashkeel, clickbait/certainty phrases, appearance descriptions, numbers or names not in the source, or too little overlap with the source. Verse lines always come from the verified Quran provider. Drafts land in `content/stories/drafts/` and need human review. A small local model can still paraphrase badly or mis-translate Urdu: review every line. Not tested against a real Ollama here (no GPU/model in the sandbox); tests use a fake model.
37. **Human-like narration is opt-in.** `audio.narration.allow_edge: true` (+ `pip install edge-tts`) uses Microsoft neural voices (en-GB-Ryan, ur-PK-Asad): far more natural than eSpeak, but online and an unofficial endpoint, so it is off by default and falls back to Kokoro/eSpeak on any error. Credited on screen as synthetic. Not testable in this sandbox.
38. **Tajweed/pronunciation/accent:** only from a real reciter's audio (EveryAyah, default Alafasy) once `permission_verified: true`. The engine never synthesizes Quran, and does not time-stretch or edit recitation. Word-level highlighting is not implemented (no verified timing data).
39. **GitHub Actions** (`.github/workflows/daily.yml`) runs the 2.5D pipeline daily; uploads stay approval-gated. Secrets are placeholders you set in the repo settings.

40. **Director's Treatment (`ivs/director.py`)** is written before each story render and stored in SQLite (`treatments`) and `treatment.json`. It is rule-based: it selects a style, pacing, grade, typography palette, camera family, composition, transition colour and silent beats from the verified script + visual-metaphor analysis + history. It does not change verses, narration or the author's environments.
41. **112-style library (`ivs/styles.py`)**: 14 categories x 8 parameter sets; every pair differs in >= 3 of 7 parameters (tested). 72 are `full` support; 40 are `approximate` (architecture, cartography, macro, photoreal, surreal) because the engine has no real architecture/map/macro/photoreal renderer: they use the nearest implemented environments, so do not expect those categories to look like their names yet.
42. **What parameters really change:** camera families + composition (3D shot paths), lighting (Blender sun/sky for daylight 3D), typography palette (colours only; same licensed fonts, no true Nastaliq/calligraphic font families added), pacing (hold lengths), colour grade (FFmpeg), transition colour (fade-through-colour, not xfade/match cuts), silent beats (no sound effects, ambience only).
43. **Environments implemented:** desert (dawn/night), mountain, sea (calm/storm/night), starry sky, and two Islamic geometric pattern spaces (2.5D). **Not implemented:** mosque interiors, underwater, forests, rain, ancient architecture, maps, volumetric light/rack focus/depth-of-field, Three.js, reflections, water simulation. No animated logo/channel identity, no true word-level highlighting, no match-cut/depth/map transitions.
44. **Hardware engine (`python -m ivs hardware`)** detects CPU threads, RAM, NVIDIA GPU/VRAM, disk and picks LOW/MEDIUM/HIGH (`three_d.tier/max_seconds: auto`). GPU rendering is requested only on HIGH and used only if Cycles finds a device. Untested on a GPU (none in the sandbox). On a LOW machine the 3D budget is 12 s per film.
45. **Visual QC (`ivs/vqc.py`)** analyses the rendered pixels: black/flat frames, contrast, crushed/blown tones, flicker, camera jitter, text-band contrast, with failing scene numbers reported (`failed_scenes`). It does not yet auto-regenerate a failed scene (shots can be regenerated by deleting their cached mp4; `scene_manifest` lists them). Arabic/Urdu shaping is checked by the glyph-coverage and raqm checks, not by OCR.
46. **Thumbnail studio** builds 3 concepts from real film frames (source title only, no invented quotes) and keeps the one with the best legibility/clarity/balance heuristic: a heuristic, not a CTR predictor.
47. **Cost auditor** (`python -m ivs audit`) now scans requirements.txt for paid packages, the environment for paid API keys, the code for paid endpoints, and prints free-tier limits. It cannot know about charges outside this project (e.g. your own cloud account).
48. **Sample length:** with Urdu + English narration the sample films run 94-143 s (target 60-120 s); trim narration or set `story_languages: [en]` for shorter films. The samples were rendered with 3D disabled (CPU time); 3D shots use the same treatment when you run `python -m ivs film <story>`.

49. GitHub Actions automation (`docs/GITHUB_ACTIONS.md`) was tested locally only (parser, YAML, state round-trip, ci-run/ci-act with YouTube off), never against real GitHub or YouTube.
50. CI renders 2.5D only; stories/hadith/drafts always need `/approve`; Testing-mode OAuth tokens expire in 7 days.
51. JS effects (PixiJS/p5/GL Transitions/HyperFrames) need Node 22 + `npm ci`; HyperFrames/Playwright browser download untested on real runners; transitions add minutes per story.
52. Lemo-Opuscar is a token-consuming agent plugin: vendored styles + brief generator only, not run, not in CI.

53. **Quran data is not bundled in the slim zip.** `scripts/fetch_quran_data.py` downloads the editions from the fawazahmed0/quran-api mirror (jsDelivr, GitHub raw fallback). With a committed `MANIFEST.json` every file must match its SHA-256 or the script exits 1. The first run without a manifest is trust-on-first-use: verify with `python -m ivs verify-data`, spot-check a printed mushaf, then commit `assets/data/`. Tested only against a synthetic local mirror (structure checks, manifest creation, tamper rejection); the real mirror URLs were not reachable from the build sandbox.
